# What KeyRingGuard proves

## Supported runtime and platforms

KeyRingGuard targets `net8.0`. The repository's filesystem integration and package-consumer checks run on Windows, Linux, and macOS in the release-equivalent CI matrix. That evidence covers the shipped filesystem fixtures, not every third-party provider or deployment environment.

## Safety and privacy

KeyRingGuard proves the behavior of the exact provider factories supplied to the scenario:

- a payload can survive independently recreated providers against the configured store; a factory that reuses one live provider instance is rejected;
- two configured replicas can exchange payloads in both directions;
- intentionally different application discriminators reject cross-provider payloads only after caller-supplied factories declare the same `KeyRingBoundary`, the control providers pass their same-boundary exchange, and the cross-check protectors implement the standard ASP.NET Core `IPersistedDataProtector` contract; arbitrary provider exceptions fail closed;
- different purposes reject cross-purpose payloads through the same standard persisted-protector rejection contract, rather than treating an arbitrary provider exception as proof;
- an explicitly requested key rotation snapshots opaque key IDs in the same bounded scheduled operation immediately before invoking the cancellation-aware key-creation callback, after linked provider and key-manager setup succeeds; it rejects a callback that returns a pre-existing key, observes exactly one matching non-revoked active key, proves a recreated provider names that key in a fresh canonical payload with the standard header, little-endian key ID, and non-empty encryptor-specific body, and keeps both old and new payloads readable. Canonical key-ID bytes remain supported when both byte orders produce identical bytes. A missing, truncated, or otherwise unsupported payload produces `RotationUnavailable` because key adoption cannot be verified; alternate byte order is unsupported only when its bytes differ from canonical. A canonical payload naming the wrong or stale key remains `RotationFailure`;
- provider construction, protector creation, protect, unprotect, key observation, and key-manager operations are observed with the configured timeout and caller cancellation. At most 32 verification lifecycles retain providers until operations, owned cancellation notifications, and best-effort cleanup finish. The 32 primary callback slots are separate from asynchronous notification dispatch, with at most one unfinished dispatch per terminating lifecycle. Stop results signal the active operation token without waiting for registrations; signaling does not promise that every registration completed. Cleanup timeout or exceptions preserve the scenario verdict; cancellation during the bounded cleanup wait returns `Canceled`. Duration includes only the work actually awaited. Arbitrary running callbacks, cancellation handlers, and Dispose cannot be interrupted and retain capacity until they return. Cleanup re-entry is guarded on flowed execution context; deliberately severed flow remains unsupported. See the authoritative [API lifecycle contract](../src/KeelMatrix.KeyRingGuard/KeyRingVerifier.cs) and [ownership guidance](usage.md#provider-factory-patterns).

Data Protection can auto-generate keys during provider initialization. A check against a real shared store may therefore mutate that store; `KeyManagementOptions.AutoGenerateKeys` controls the caller's provider behavior. Use temporary or dedicated stores by default and make deliberate shared-store mutation explicit.

KeyRingGuard does not prove that a store has a valid backup, disaster-recovery process, HSM configuration, access-control policy, network reliability beyond the exercised operation, key escrow, or production-wide fleet consistency. It is not a key vault, a backup service, a replacement cryptography implementation, a CVE scanner, a health endpoint, or an authentication-cookie parser.
