# Release validation

## Website discovery metadata

The root [`keelmatrix.website.json`](../keelmatrix.website.json) declares `KeelMatrix.KeyRingGuard` as `public-product` and `primary` in schema version 1. It contains classification only. The shipping project's `PackageTags` preserves its search tags and includes exactly one lowercase visibility sentinel, `keelmatrix-public-product`, and one role sentinel, `keelmatrix-primary`. Keep the canonical GitHub project and repository URLs pointed at `https://github.com/KeelMatrix/KeyRingGuard`; the project URL also accepts its existing `#readme` fragment.

Run `pwsh ./scripts/Test-WebsiteMetadata.ps1` for evaluated Release source validation and `pwsh ./tests/VerifyWebsiteMetadataContract.ps1` for negative controls. The validator discovers `.csproj`, `.vbproj` and `.fsproj` files throughout the repository, including tests, smoke consumers, examples and tools. Extension matching and the exclusion of generated `bin`, `obj`, `artifacts` and `.git` directories are case-insensitive. Real SDK evaluation includes inherited props/targets, project overrides and Release conditions. Only `src/KeelMatrix.KeyRingGuard/KeelMatrix.KeyRingGuard.csproj` may be packable; adding a manifest entry cannot authorize another shipping project. Exact manifest IDs, classification, canonical URLs and one public primary must match the evaluated source.

With `-PackagePath <path.nupkg> -SymbolPackagePath <path.snupkg>`, the same check validates each archive's actual root nuspec against the manifest and source, preserving every source tag. Either archive parameter can also be used alone. Missing or ambiguous metadata, malformed XML/DTDs, ID/URL/type drift and tag drift fail. `Inspect-Package.ps1` requires the matching symbol archive and checks both nuspecs before payload, README, icon, PDB or SourceLink acceptance. After packing, run `pwsh ./tests/VerifyWebsiteArchiveContract.ps1` for independent mutations in each archive and a valid real-package control. Its synthetic archives contain nuspecs only. Local validation, every CI OS leg and release validation run the source and paired-archive fixtures. Required failures stop later steps; release inspection and fixtures precede artifact upload, and publication depends on that validation.

Published NuGet versions are immutable. Existing versions without sentinels use the public repository manifest as the website's migration fallback. Future normal releases carry the source sentinels and must agree with the manifest. Do not republish or change a version solely for classification metadata. A valid manifest permits discovery; it does not prove a live catalog refresh or listing.

## SDK prerequisites

`global.json` is the source of truth for SDK selection: stable `10.0.401`, `rollForward: patch`, `allowPrerelease: false`. Local CLI and Visual Studio builds prefer exactly `10.0.401` when installed; otherwise they select the highest installed stable servicing patch at or above that minimum within `10.0.4xx`. Earlier patches, other feature bands, major/minor versions and previews cannot substitute. Installing only a .NET 8 SDK/runtime or a .NET 11 preview does not meet the source-build prerequisite. The shipping package still targets `net8.0`.

Visual Studio 2026/MSBuild 18.0 or later is required by SDK `10.0.4xx`; its paired Visual Studio version is 18.9. Visual Studio 2022/MSBuild 17.x is not supported for this source build. See Microsoft's [SDK/Visual Studio version matrix](https://learn.microsoft.com/en-us/dotnet/core/porting/versioning-sdk-msbuild-vs) and [global.json selection rules](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json). The explicit preview exclusion applies even in an Insiders IDE or with preview SDKs enabled.

Each CI and release CLI job independently installs exactly `10.0.401` and runs `scripts/Test-SdkSelection.ps1 -RequireExact` before other commands. The `patch` policy prefers that installed baseline, keeping compiler, analyzers, release identity evaluation and publication on the same exact SDK. Missing provisioning or a different selected SDK fails the job. Local validation uses `scripts/Test-SdkSelection.ps1` and records the selected servicing version; it is not an exact-baseline release certification.

For NETSDK1141 or an SDK-not-found error, run `dotnet --list-sdks` and `dotnet --version` from the solution directory, then check the Visual Studio version separately. Install the baseline or a permitted stable servicing patch and use a compatible IDE. Close and reopen the solution after installing prerequisites. The CLI starts its global.json search at the working directory; the IDE resolver starts at the solution/project, so a CLI success elsewhere does not prove the solution can load. A preview SDK path in the IDE error can be a fallback after the requested SDK failed to resolve. Changing preview settings is not required by this repository.

[`scripts/Test-ChangelogContract.ps1`](../scripts/Test-ChangelogContract.ps1) and its [executable fixtures](../tests/VerifyChangelogContract.ps1) own the release contract. The validator classifies original physical blocks, validates heading ancestry, projects supported visible text, then checks real XML declarations and evaluated Release identity. Inline processing cannot create a block or change its parent.

The supported Markdown subset is deliberately finite. Unsupported syntax fails in both modes:

- Input is valid UTF8 with an optional initial BOM, LF or CRLF, and an optional terminal newline. Narrative uses printable ASCII; bare CR, control characters, non-ASCII narrative, and structural tabs fail. Literal examples and comments may contain uninterpreted text.
- One literal H1 `Changelog` contains one real H2 `[Unreleased]` and one real target H2 `[X.Y.Z] - yyyy-MM-dd`. ATX headings have zero to three leading ASCII spaces, an ASCII-space separator and optional trailing spaces. Closing hashes, Setext headings, inline heading markup, extra H1s and skipped ancestry fail. Four spaces or a tab cannot supply a heading. Indented headings attached to prose or lists are ambiguous and fail.
- For 0.1.0, exactly one direct H3 `Added` contains a substantive capability bullet. Content before Added, examples, empty/comment-only/punctuation-only bullets and extra categories cannot supply it. Plain H4-H6 headings may supplement a category with complete ancestry. Other versions support the direct categories Added, Changed, Deprecated, Removed, Fixed and Security.
- Prose and flat column-zero bullets (`-`, `*` or `+`, then exactly one space) support plain soft wraps. Nested, ordered, task and indented lists, tables, link definitions and ambiguous container continuations fail.
- Complete backtick or tilde fences use at least three markers, zero to three leading spaces, and the same closing marker with at least the opening length followed only by spaces. Backtick info cannot contain a backtick. An indented fence attached to prose or a list requires a blank boundary. Comment delimiters in fence info/body are literal.
- Quoted examples require an explicit `>` on every nonblank line and a blank exit boundary or EOF. Indented examples start at a blank-separated top-level boundary with at least four spaces or a tab and require a blank exit boundary or EOF. Lazy quotes and partial/ambiguous example continuations fail.
- Block comments begin with `<!--` as the first nonspace text with zero to three leading spaces. Opening, interior and closing physical lines supply no evidence. The first `-->` must have only whitespace after it; any visible suffix, even another comment, fails. Nested, malformed and unclosed comments fail. Comment state owns fence-looking text.
- Within already classified prose/bullets, complete same-line inline comments are removed without inserting characters. Multiline inline comments, stray delimiters and heading comments fail. Balanced nonempty single-backtick code spans on one physical line preserve their literal printable content; edge whitespace and multi-backtick spans fail. Code owns comment-looking syntax.
- Outside code/comments, entities (`&`), raw HTML (`<`/`>`), backslash escapes, emphasis (`*`/`_`), strikeout (`~`), brackets and pipes are unsupported, including when used in finalized prose. They are rejected, never stripped or decoded into a second parse.

Visible text retains headings, prose and code, joins soft lines with spaces and removes only supported inline comments. Strict validation rejects planned, unreleased, pending, TBD, unpublished, not published, not yet published and pre-release states case-insensitively, including space/hyphen variants. Inline code cannot hide them. First-release remediation backstops use that same projection: now, no longer, previously, formerly, used to, fixed/fixes, corrected, resolved, addressed, this removes/this fixes and changed from. These finite lexical checks do not replace semantic editorial review. Dates use the invariant calendar and cannot exceed the current UTC date.

The source graph consists of root `Directory.Build.props`, root `Directory.Packages.props`, the shipping project and optional root `Directory.Build.targets`. `-RepositoryRoot` selects that graph; `-ShippingProjectPath` selects an explicit within-root project, defaulting to `src/KeelMatrix.KeyRingGuard/KeelMatrix.KeyRingGuard.csproj`. Optional changelog/version path parameters must remain inside that root; version paths must select its actual root files. Nearer shadow props/targets/central files, explicit repository imports, namespaces, DTDs, processing instructions and unsupported version-source layouts fail.

Real XML must contain exactly one unconditional direct `Project/PropertyGroup/Version` with canonical X.Y.Z components in 0..65534, one unconditional literal `PackageVersion=$(Version)` property alias in that props file, and one unconditional direct central `Project/ItemGroup/PackageVersion` item for `KeelMatrix.KeyRingGuard`. Central items use only literal Include/Version attributes. XML comments cannot supply declarations. Conditional leaf/group declarations, duplicates (even equal or inactive), VersionPrefix/Suffix, target-produced versions, derived values and child/CDATA version content fail. Unrelated existing build/pack conditions remain supported.

From `RepositoryRoot`, SDK selection first passes `dotnet --version`: strict release mode requires exactly the `global.json` baseline; `-Readiness` also accepts its permitted local servicing patches. A bounded real query then runs with no version override:

```text
dotnet msbuild <shipping-project> -nologo -p:Configuration=Release -getProperty:Version,PackageVersion,PackageId,TargetFramework,ManagePackageVersionsCentrally -getItem:PackageVersion
```

This executes no targets and needs no restore or `obj` directory. Evaluated Version and PackageVersion must equal the tag and real declarations, with the intended package ID, net8.0 target, enabled central management and exactly one matching central shipping item from the intended central file. Missing SDK/items, nonzero exit, timeout, invalid JSON and disagreement fail without a text-only fallback. Actual package inspection separately establishes what pack produced; this query does not analyze arbitrary MSBuild programs.

Ordinary CI runs the executable finalized/draft fixtures and `-Readiness` against the repository entry. Readiness accepts a valid dated heading or the exact draft suffix `Planned (not yet published)` and allows draft narrative; grammar, substantive content, version agreement and first-release editorial checks still apply. The tag workflow omits `-Readiness`, checks its exact commit and requires a dated finalized entry before restore/build/pack/upload/authentication/publication. A readiness pass is not publication validation.

`scripts/Publish-ReleaseArtifacts.ps1` accepts exactly the intended `.nupkg` and `.snupkg` files. The primary push uses `--no-symbols`; one subsequent explicit symbols push uses the V3 symbol resource. Both commands use explicit source/configuration and bounded execution. A primary failure prevents symbols. A symbols failure preserves confirmed primary submission and reports symbol acceptance as uncertain. Neither command is automatically replayed by the script; the CLI transport can retry individual requests. A lost response does not establish whether the server accepted bytes. Successful submission does not establish indexing or consumer availability.

`tests/VerifyPublicationContract.ps1` executes the validated CLI (exact baseline in CI, permitted servicing patch locally) against a finite loopback-only V3 fixture, with synthetic artifacts/credentials, cleared configuration, no external resources, and no redirects. It checks actual upload counts/hashes, pending symbols, partial/unknown outcomes, invalid artifact sets, and the automatic-symbols negative control. This proves client execution, not NuGet.org validation or indexing. `-DryRun` only previews the chosen commands.

Run the affected validator fixture first. `scripts/Invoke-LocalGate.ps1` provides the full local validation path; `.github/workflows/ci.yml` runs the corresponding checks on Windows, Linux, and macOS. The shared checked-step runner and `tests/VerifyGateOrchestration.ps1` verify that a failed child prevents later operations.
