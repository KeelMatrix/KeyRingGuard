# Privacy

KeelMatrix.KeyRingGuard performs verification locally and does not collect or transmit telemetry. It does not contact a network unless the caller-supplied provider factory does so.

Verification uses a random, bounded, in-memory canary. The canary, protected payload, key XML, key identifiers, backing-store paths, application names, and provider exception text are not returned in diagnostics.

Timeout results do not change this privacy boundary. A synchronous caller callback that continues after a timeout remains outside KeyRingGuard's diagnostics and telemetry surface; its provider is retained until the callback completes and is then disposed. The shared scheduler has 32 callback slots and honors caller cancellation while admitting queued work. A nested verification started on a callback's own flowed execution context returns `InvalidScenario` before another scheduled operation can expose caller state. A callback that deliberately severs flow with `ExecutionContext.SuppressFlow`, `ThreadPool.UnsafeQueueUserWorkItem`, or a new thread is outside this guard and unsupported. Isolation does not treat an arbitrary provider exception as proof: after the same-boundary control passes, only the standard ASP.NET Core `IPersistedDataProtector` contract can turn a cross-check `CryptographicException` into an isolation success. Rotation snapshots only opaque key IDs in the same bounded scheduled operation immediately before invoking the callback to reject no-op/pre-existing-key callbacks; those IDs are not returned in diagnostics. A missing, truncated, alternate-endian, or otherwise noncanonical recreated payload produces `RotationUnavailable`, while a canonical payload naming the wrong key produces `RotationFailure`. Rotation callbacks must honor cancellation before changing caller-owned key-store state.
