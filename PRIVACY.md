# Privacy

KeelMatrix.KeyRingGuard performs verification locally and does not collect or transmit telemetry. It does not contact a network unless the caller-supplied provider factory does so.

Verification uses a private random, bounded, in-memory canary. Callbacks receive working copies; returned byte evidence is captured inside the callback boundary before later calls can reuse its storage. The canary, protected payload, key XML, key identifiers, backing-store paths, application names, and provider exception text are not returned in diagnostics.

Timeout and cancellation do not change this privacy boundary. Providers remain owned until operations, owned cancellation notifications, and best-effort cleanup finish, including late work. Final-cleanup exceptions are suppressed without exposing provider details. Failed restart retirement prevents recreation and returns a sanitized failure. Independent callback cancellation is not attributed to a deadline or caller stop. The 32 lifecycle reservations and shared 32 callback slots bound retained work; asynchronous notification dispatch retains at most one unfinished dispatch per terminating lifecycle. Caller observation remains bounded even when cancellation handlers or cleanup block. Stop results signal the active token without waiting for registrations, and notification exception text is never emitted. Callback re-entry on flowed execution context is rejected, including cleanup; deliberately severed flow remains unsupported. See the authoritative [API lifecycle contract](src/KeelMatrix.KeyRingGuard/KeyRingVerifier.cs) for waiting, ownership, and Duration semantics. Isolation does not treat an arbitrary provider exception as proof: after the same-boundary control passes, only the standard ASP.NET Core `IPersistedDataProtector` contract can turn a cross-check `CryptographicException` into an isolation success. Rotation snapshots only opaque key IDs in the same bounded scheduled operation immediately before invoking the callback to reject no-op/pre-existing-key callbacks; those IDs are not returned in diagnostics. A missing, truncated, or otherwise unsupported envelope produces `RotationUnavailable`, while a canonical payload naming the wrong key produces `RotationFailure`. Rotation callbacks must honor cancellation before changing caller-owned key-store state.
